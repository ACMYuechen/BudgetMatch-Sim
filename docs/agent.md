## 2. 现有接口、会话与长期记忆

推荐接口使用 `conversation_id` 关联同一认证用户的多轮上下文，并使用 `turn_id` 保证单轮请求幂等。首次请求可不传 `conversation_id`，服务端生成后返回；前端应为每次发送生成新的 `turn_id`，网络重试沿用原值。

RPC 不再接受 `user_id`。Agent RPC 只信任认证拦截器写入的用户身份；即使两个用户使用相同 `conversation_id`，数据也按 `user_id + conversation_id` 隔离。

### 2.1 调用示例

首次请求：

```http
POST /api/agent/recommend
Authorization: Bearer <token>
Content-Type: application/json

{
  "query": "预算 3000 元，想配一套学习桌面",
  "budget_cents": 300000,
  "max_items": 3,
  "turn_id": "1f2e1ad7-cb89-47bb-b64b-4f86f6e99077"
}
```

响应会返回稳定的会话与轮次标识：

```json
{
  "conversation_id": "4f73fd97-7a89-41ae-90cb-4a9e27de941c",
  "conversation_title": "预算 3000 元，想配一套学习桌面",
  "turn_id": "1f2e1ad7-cb89-47bb-b64b-4f86f6e99077",
  "summary": "..."
}
```

继续同一会话时只填写本轮需要覆盖的结构化约束。下面没有传 `max_items`，所以会继承上一轮的 3 件：

```json
{
  "query": "预算增加到 5000 元，优先机械键盘",
  "budget_cents": 500000,
  "conversation_id": "4f73fd97-7a89-41ae-90cb-4a9e27de941c",
  "turn_id": "c026238c-710f-45d6-952a-fbb44f3c761c"
}
```

重复提交相同 `turn_id` 且请求内容一致时，服务直接重放已保存结果，不会再次调用模型或新增轮次；工具记录经过当前脱敏规则过滤，旧正文不会随重放返回。如果复用同一 `turn_id` 却修改 `query`、`budget_cents` 或 `max_items`，接口返回 HTTP 409，防止把旧结果误认为新请求的响应。

### 2.2 请求边界

- `query` 必填，去除空白后不得为空，原始长度最多 2000 个字符；
- `budget_cents` 范围为 0 到 100000000000，0 表示交给文本解析或继承上一轮；
- `max_items` 范围为 0 到 10，0 表示交给文本解析或继承上一轮；
- `conversation_id` 与 `turn_id` 最多 128 个字符，不允许首尾空格；首次请求可留空并由服务端生成。

HTTP 网关和 Agent 业务服务都会执行边界校验，因此直接 RPC 调用也不能绕过这些规则。

#### 文本约束解析

预算、件数逐字段采用以下优先级：当前请求的非零结构化值 → 当前文本 → 已保存结构化状态 → 最近可用历史文本 → 默认值（3000 元、3 件）。结构化值已经明确的字段不再由低优先级文本覆盖；原始请求不会被解析结果改写。

目前采用确定性的有限文法，不依赖模型猜测预算。金额统一为人民币：支持 `元/块/人民币/CNY/RMB/yuan/￥/¥`；明确预算语境中不带币种也按人民币处理。识别到美元、欧元、日元等外币时拒绝，不自动换汇；`¥` 在本项目内按人民币解释，不能用于表示日元预算。

| 文本示例 | 行为 |
| --- | --- |
| `预算19.99元`、`预算1,000.50元` | 精确得到 1999 分、100050 分，支持合法千分位 |
| `预算1.001千元`、`预算0.000001万元` | 先按量级精确换算，再验证能否表示为整数分 |
| `预算3-5k`、`budget 3000 to 5000` | 正向金额区间取上限；两端均需合法 |
| `预算改成50元`、`预算降到30元`、`预算降低至19.99元` | 作为本轮绝对预算上限；支持“减少到/下调为”等明确目标表达，件数仍按原优先级继承 |
| `预算减少50元`、`预算降低了50元`、`预算下调50%` | 不支持相对金额/比例运算，返回预算错误，不将变化量当成新上限 |
| `预算0元`、`预算-500元`、`预算19.999元` | 返回预算错误，不继承历史、不用默认值、不截断亚分金额 |
| `预算$500`、`预算JPY500` | 返回币种错误 |
| `预算3000元，预算5000元`、`预算3000或5000` | 返回歧义错误；同值的重复上限可接受 |
| `最多两件`、`只买一件`、`at most two items` | 解析为最多 2、1、2 个推荐条目；支持阿拉伯数字、一至十（含两）、one 至 ten |
| `最多十一件`、`最多1.5件`、`最多2-3件`、`至少3件` | 返回件数错误，不猜测或截断数量 |
| `预算1000元，耳机价格300-500元` | 明确预算优先于普通商品标价，预算仍为 1000 元 |
| `iPhone 15`、`4K`、`65W`、`一套学习桌面`、`三件套床品` | 不作为预算或整体条目数上限 |

仅支持预算上限和最多条目数，不支持最低消费、最低件数、无限预算或逐 SKU 购买数量。单个数量描述可作为最多条目数，但不保证购买该数量；多个商品数量描述没有明确总上限时拒绝推断。中文金额数字（如“三千元”）、科学计数法和未能完整解析的明确预算表达会要求用户重新填写；“预算不变”可继承历史。复杂需求分解、澄清状态和数量建模仍属于后续工作，不能据此宣称任意自然语言都可正确解析。

错误经 RPC 映射为 HTTP 400，并在现有错误码序列末尾追加，不改变旧错误码：

- `400007`：预算币种不支持，提示改用人民币或 `budget_cents`。
- `400008`：预算非法、超界或有歧义，提示填写唯一、精确到分的正数上限。
- `400009`：件数非法或有歧义，提示填写唯一的 1～10 件上限。

解析失败不会调用模型、查询商品或触发规则兜底，不保存完成轮次，也不改写会话状态；修正后可重试未完成轮次。已完成轮次仍重放原结果，不对旧文本重新解释。

### 2.3 推荐结果约束

- 服务端解析出的预算和件数是本轮上限；模型工具传入 `0` 时继承、负数拒绝、更大正数收紧到该上限。
- 推荐商品按 SKU 去重，过滤非法价格和无库存候选；保存前校验条目与本轮商品快照、预算、件数和总价一致。不合法的兜底结果也不能保存。
- 当前 Summary 使用服务端核验后的件数、总价和预算生成，不直接展示模型自由文本，避免摘要与商品卡片矛盾。
- 原始请求仍单独保存，约束解析不会改变 `turn_id` 的请求比较语义；已完成轮次保持原结果重放。
- 上述校验不代表库存预占或实时价格保证，下单前仍需商城确认。工具权限见第 2.8 节，效果评测及商品实时校验等剩余工作见[验证入口与执行清单](#13-验证入口与执行清单)。

### 2.4 管理接口

- `GET /api/agent/conversations?page=1&page_size=20`：按最近更新时间倒序列出当前用户会话。
- `GET /api/agent/conversations/:conversation_id/turns?page=1&page_size=50`：恢复会话状态与完整轮次。
- `DELETE /api/agent/conversations/:conversation_id`：删除当前用户的会话和全部轮次。
- `POST /api/agent/recommend/stream`：与同步接口使用相同鉴权、`conversation_id` 和 `turn_id` 语义。

前端路由 `/recommend/:conversationId` 会在刷新或跨设备打开时重新加载服务端历史；未登录访问会先跳转登录页。

当前 SSE 仅包装网关阶段事件，底层仍是 unary RPC，不是模型 Token 或工具调用级真实流式；端到端流式属于 [M5 计划](#10-m5端到端流式运行预算与可观测性)。

### 2.5 PostgreSQL 数据模型

当前会话表结构与旧消息表不兼容；已有旧数据的环境需单独规划迁移。

- `agent_conversations`：复合主键为 `user_id + conversation_id`，保存稳定标题、最新结构化 `state`、版本、轮次数与时间；
- `agent_conversation_turns`：复合主键为 `user_id + conversation_id + turn_id`，保存轮次序号、原始请求、输入预算/件数、解析意图、完整推荐结果和完成时间；
- `user_id + conversation_id + sequence` 有唯一索引，删除会话时轮次通过复合外键级联清理。

PostgreSQL 模式不应用 `Memory.TTL`，因此服务重启或间隔数天后仍能恢复。只配置 Redis 或未配置外部存储时仍是短期记忆，分别受 Redis TTL 或进程生命周期约束。

### 2.6 两级缓存

同时配置 `Database.DSN` 与 `CacheRedis` 时，PostgreSQL 是唯一事实源，Redis 只缓存最近 `MaxHistory` 条消息快照：

```text
写入：同会话锁 → PostgreSQL 事务保存会话与轮次 → 版本递增 → Redis 快照失效
读取：查询 PostgreSQL 版本 → 命中同版本 Redis 快照；否则回源并回填
```

Redis 故障只降低缓存命中率，不覆盖 PostgreSQL。只配置 Database 时直接读写 PostgreSQL；只配置 CacheRedis 时使用 Redis 短期会话；均未配置时使用 InMemory。

### 2.7 状态、上下文与并发边界

- 预算、最多件数、关键词和偏好以结构化状态持久化，不依赖旧文本是否还在短期窗口；当前轮明确值优先。
- `Memory.MaxHistory` 控制注入模型的最近文本消息数；`Memory.MaxContextTokens` 是系统提示、当前请求和历史消息的严格近似总上限。历史按完整轮次从旧到新淘汰；系统提示与当前请求自身超限时返回 400，不会截断问题或悄悄降级。
- InMemory 使用进程内会话锁，Redis 使用带令牌的分布式锁，PostgreSQL 使用连接级 advisory lock。相同用户的同一会话按顺序执行与删除，不同用户或不同会话可并行。

### 2.8 文件工具与 MCP 权限

默认只注册 `search_products` 和 `select_bundle`，不创建文件工作区、不启动 MCP。操作员配置示例（默认保持关闭）：

```yaml
FileTools:
  Enabled: false
  AllowWrite: false
  Workspace: "workspace/agent"
  MaxReadBytes: 65536
  MaxWriteBytes: 65536
  WritableExtensions: [".json", ".md", ".txt"]
MCP:
  Enabled: false
  Command: ""        # 已安装且经审计的可执行文件绝对路径
  Args: []
  AllowedTools: []    # 服务端原始名称，最多 16 项，不支持通配符
  Timeout: 5000      # 每次初始化/发现/调用超时，最大 30000 ms
```

文件能力目前仅支持 Linux；其他平台启用时拒绝初始化。`WritableExtensions` 保留原配置名，但同时约束读取与写入，只能配置 `.json/.md/.txt` 的子集。单次读写默认 64 KiB，配置硬上限 1 MiB；工具整体入参/结果另限 256 KiB，JSON 包装开销可能使实际可用文件大小更小。

启用文件工具后，由 RPC 认证身份映射到 `<Workspace>/users/<SHA-256(user_id)>`，模型不能指定用户。目录权限 0700、新文件 0600；根句柄约束路径解析，拒绝越界、隐藏路径、非法文件类型、非普通文件、末级符号链接与硬链接读取。同一用户的不同会话共享私有文件，不提供管理员跨用户入口。路径最长 512 字节、最多 8 层；配置根目录及挂载应由运维控制。[Go 官方目录句柄说明](https://go.dev/blog/osroot)解释了为何不能仅靠“检查路径后再打开”防御并发路径替换。

写入必须同时满足 `Enabled: true`、`AllowWrite: true` 和本轮原始 query 首行保存指令，例如：

```text
/save recommendations/desk-20260917.md
预算3000元，最多三件学习用品，请把推荐保存成报告
```

第二行起必须有购物请求；保存路径不参与预算、关键词或历史约束解析。只有这一轮会注册 `write_file`，只允许指定路径的一次创建，不覆盖旧文件；模型、历史消息或工具内容不能产生新授权。指令授予能力，不保证模型一定调用写入；目前公开 Summary 仍是确定性商品摘要，可从 `ToolsUsed` 查看写入执行状态。文件写入与会话事务分离：发布后取消或保存会话失败可能留下文件，重试会因文件已存在而失败，不能宣称外部副作用 exactly-once。关闭模型或进入规则兜底时不执行文件保存。

授权读取的文件内容会作为工具结果发送给配置的模型；不要把密钥、Token 或不允许发送给该模型的数据放入工作区。旧版共享目录不会自动迁移，删除会话也不会删除用户文件；迁移归属、容量配额与清理策略需单独安排。本次不操作真实工作区。

MCP 只有非空精确白名单才启动，且被允许工具必须声明 `readOnlyHint=true`，缺失、重名或非只读声明会拒绝加载。发现与调用双重校验，发现最多 8 页/128 个描述符；模型工具名统一加 `mcp_`，不允许冒充内置工具。不转发认证 Header/Meta，不自动下载服务端，不继承 JWT、数据库、模型密钥或代理环境变量；使用私有临时工作目录，超时/请求结束回收进程组并清理目录，stderr 不入日志。

白名单和只读声明不是安全证明：受信任服务端仍以服务 OS 身份运行，可访问该身份可访问的文件和网络，不能视为容器、文件系统或出网沙箱；脱离进程组的恶意子进程也不在清理保证内。只接入操作员已审计的只读服务，不开放下单/支付；按角色工具清单、进程并发配额及 OS/网络隔离仍待进一步部署治理。

### 2.9 工具记录与日志

Agent 自有日志/Eino 回调只记录执行状态、稳定错误分类、数量、字节数、耗时、Token 用量和分数区间，不记录查询、参数、文件/工具正文或原始异常。外部模型/工具名称以稳定摘要标识，Agent 自有日志中的用户/会话 ID 也使用摘要。RPC 错误保留取消、超时和权限语义，消息不暴露底层错误。

`ToolsUsed` 在执行记录、持久化、历史查询和幂等重放边界都过滤为静态说明及已知数值元数据；旧数据库字段和旧日志不会被追溯改写。本轮不脱敏用户正常业务输入/商品结果，也不承诺其他微服务、数据库驱动、网关访问日志或外部模型服务已统一脱敏；相关风险仍见 [权限控制现状](access-control.md)。

### 2.10 后台索引配置（M3.1 / M3.2）

Agent 后台通过 `mall.ProductIndexService/ScanProductIndex` 读取商品目录快照；旧 `ListProductIndex` 保留给旧客户端，但新 Loader 不调用它。在线搜索及必需的 `CheckProductCandidates` 最终校验继续透传用户 JWT，使用不同 RPC 客户端，不使用索引服务身份。

- Mall 与 Agent 的 `IndexAuth.Secret` 使用同一个独立的 `AGENT_MALL_INDEX_SECRET`，至少 32 字节、无首尾空白；必须由操作员生成密码学安全随机值，不复用用户或支付密钥。模板和 Compose 已提供变量传递，本步未读取、生成或改写真实 `.env` / 集群 Secret。
- Mall 未配置索引密钥时，该接口拒绝全部请求，旧用户/支付接口仍可用；若配置了索引密钥，启动前检查其与 `JWT_SECRET`、`ServiceAuth.Secret` 不同。Agent 已声明 Database＋Embedding＋Mall 时，缺少/过短/复用用户密钥会在外部依赖初始化前阻止启动，不静默降级；未声明 RAG 时仍支持规则/关键词模式。
- 每次索引 RPC 签发有效期 1 分钟、用途为 `product-index:read` 的服务 JWT。Mall 校验 HS256、`service/iss/sub=agent-rpc`、受众含 `mall-rpc`、用途、时间字段和 `jti`，有效期上限 5 分钟；没有一次性消费表，不能声称防重放或 mTLS。
- 索引接口固定读取未软删除且 SPU/SKU 均上架的数据，只返回索引所需字段，不包含商品所有者、内部评价、订单或支付数据。按 SKU ID 字节序分页，默认 100、最多 200 条。新流式扫描使用同一数据库快照，完成帧与数据帧分离；Loader 拒绝异常空页、重复/倒退 ID、序号/身份变化及部分失败（第 2.12 节）。旧一元分页仍使用额外一行判断末页，不提供跨 RPC 快照保证。
- 切换真实环境时先更新 Mall，再配置双方凭据、更新 Agent；旧 Mall 返回 `Unimplemented` 或鉴权失败时不清理旧索引，也不回退到免鉴权接口。
- M3.2a 新增 `CatalogScan.Complete` 契约：扫描未明确完成时禁止发布，即使返回空列表且没有错误。完整扫描先校验所有文档及唯一 SKU，再准备变更向量；价格/库存/销量只变更业务快照，不新增嵌入。可选 Transformer 必须保留一 SKU 一文档及商品身份，不能通过丢弃文档扩大清理范围。
- 准备结果与原扫描逐行核对后，向量 upsert、业务快照刷新和下架清理在同一短事务内发布；事务不跨越 Mall/Embedding 请求。提交前失败或取消会回滚；提交确认丢失仍可能存在结果不确定性，不能承诺任何错误都代表“数据库没有提交”。
- `RAG.SyncTimeoutSeconds` 默认 300 秒、上限 3600 秒，是一轮扫描/嵌入/发布的共同期限；`RAG.SyncStopTimeoutSeconds` 默认 5 秒、上限 30 秒，是进程关闭钩子的最大等待时间。两者缺省或非正数取默认值，超过上限则收敛；不新增环境变量。`SyncIntervalSeconds` 仍为 0 时默认 600 秒、负数仅启动同步一次。
- `Start` / `Stop` 幂等且停止后不能重启；关闭立即取消当前轮并有界等待。同一个 Pipeline 拒绝重叠同步。各阶段边界检查取消状态，已成功提交的数据不会因随后取消而撤回；不响应 context 的外部调用无法被强制终止，有界返回不代表该调用已退出。批次日志记录随机批次 ID、起止时间、数量、耗时及静态错误分类，不记录目录正文或原始异常。
- 新 Mall Loader 的 `Complete` 表示快照事务已结束、协议完整且收到正常 EOF，不等于候选在用户看到结果时仍然新鲜；M3.2c 另在返回前校验（第 2.13 节）。M3.2b1 在本地互斥之外增加数据库会话协调，并移除了维度变化自动删表重建路径，适用条件与升级限制见下节。

### 2.11 索引写入协调与模型绑定（M3.2b1）

索引写入顺序为：获取专用数据库会话及固定锁 → 校验模型绑定 → 完整扫描/嵌入准备 → 原连接中的短事务发布 → 废弃该连接。Pipeline 在扫描前获取锁，不能只在提交时加锁，否则早开始但慢完成的扫描仍可晚于新扫描覆盖索引。独立 Eino `Indexer.Store` 也在嵌入/写入前获取锁，但其传入文档的新鲜度由调用方负责，不能代替完整同步 Pipeline；未持有会话的 hash 查询、upsert、快照刷新及清理直接拒绝。

- 同一数据库使用固定 `pg_try_advisory_lock` 键，不按模型分配不同锁。争用时不排队扫描：后台跳过本轮，初始化则拒绝本次启动、由操作方重试。外部 Mall/Embedding 调用期间保留一条连接，但不持有 SQL 事务；只有初始化或最终发布使用短事务。
- 完成、错误、panic 或取消均废弃该物理连接；不会仅调用 `sql.Conn.Close` 将持锁会话放回空闲池。取消通过 `context.AfterFunc` 提前使连接失效，旧任务即使迟到返回，也不能重连发布。这里利用的是会话结束释放锁、连接状态固定在专用连接上的语义，见 [PostgreSQL advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) 与 [Go Conn.Raw / Close](https://pkg.go.dev/database/sql#Conn.Raw)。
- `product_vector_profile` 是新增的单行模型绑定表，存储 SHA-256 指纹和维度；指纹覆盖有效 Provider、规范化 BaseURL、有效模型名及维度，不包含 `APIKey` 字段。仅轮换 APIKey 不改变绑定；端点/模型名变化，即使维度相同也不允许混用。空默认地址与显式地址保守视为不同身份；它是配置身份，不是模型权重校验，无法识别服务商在同一别名背后替换权重。
- 初始化在同一锁和事务中创建必要结构、检查实际向量维度、绑定模型并确保索引；入口有 30 秒期限。每轮同步再次核对绑定，向量检索也在同一条 SELECT 中限定绑定指纹/维度，避免把不同模型的向量当成当前索引返回。公开旧写入方法不能绕过持锁会话；Indexer/Prepare/Retriever 拒绝通过 Eino `WithEmbedding` 临时替换模型，TopK 等非模型选项仍可使用。

| 索引现状 | 初始化行为 |
| --- | --- |
| 新库或空向量表，尚无绑定 | 在事务内建立当前模型绑定 |
| 绑定与实际维度均匹配 | 幂等通过，不重嵌入 |
| 非空旧索引，无绑定记录 | `ErrUnboundIndex`，保留数据并拒绝启动 |
| 绑定不匹配或实际向量维度不符 | `ErrProfileMismatch`，不删表、不覆盖绑定 |
| 另一实例正在持锁同步 | `ErrSyncBusy`，本次初始化失败，不抢占写入者 |

升级与运维边界：

- **有存量索引时不是直接滚动升级**：必须先停止所有旧版同步器/写入进程并确认模型来源，再单独制定和授权绑定迁移或影子索引重建。旧版不会遵守新锁；只改配置重启、删除绑定表、填一个未经核实的指纹都不是安全迁移。当前未提供自动接管旧索引或一键重建开关，也没有执行任何真实迁移。
- 必须直连 PostgreSQL，或使用保持服务端会话且保证客户端断开后重置/释放 advisory lock 的 session pooling；未验证此释放行为的代理不在支持范围内。transaction pooling 不能保证锁与写入属于同一服务端会话，不受支持。每个活跃同步轮占一条数据库连接，结束后关闭驱动连接，连接池容量及少量重连成本需纳入部署预算。
- 锁是协作协议，不会拦截手工 SQL、旧二进制或不遵守协议的其他写入者；未在真实数据库、多进程、网络分区或代理上完成验收。连接释放在服务端被观察到前，其他实例仍可能显示 busy，不承诺瞬时故障接管。
- 取消不能强制终止不响应 context 的外部请求；旧请求可能与接手实例的外部工作暂时并存，但旧写入连接已经失效，不能恢复发布。不存在付费调用 exactly-once 保证。
- 会话协调只保护目标索引写入，不让 Mall 的多页查询自动变成一致快照。源端另由 M3.2b2 的快照事务保证读取一致性（下一节），最终候选另由 M3.2c 校验（第 2.13 节）。

### 2.12 Mall 跨页一致快照（M3.2b2）

新增 `ProductIndexService.ScanProductIndex` 服务端流式 RPC。Mall 使用一个 `sql.LevelRepeatableRead`、`ReadOnly=true` 的事务读取全部页；后续分页继续使用事务连接，不重新从连接池读取实时页。PostgreSQL 的该隔离级别让后续查询使用第一次非事务控制语句建立的同一快照，避免扫描中途的插入、更新、下架或删除混入后页；这不等于业务操作的串行化或最终推荐的实时状态，见 [PostgreSQL 事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-REPEATABLE-READ)。

- 每个流分配随机 UUID `snapshot_id`；它只用于协议内的身份一致性检查，不是可导出/恢复的 PostgreSQL 快照、签名或 checkpoint。`sequence` 从 1 连续增长，数据帧带本页最后的 SKU ID；短数据页之后只能结束，不能继续追加数据。
- 数据页在只读事务中顺序发送；事务成功提交后，发送单独的空完成帧（`complete=true`、总条数、无游标）。Agent 必须再收到正常 EOF，才设置 `CatalogScan.Complete`。断流、晚到错误状态、重复终帧、跨快照身份、计数/序号不一致及超限全部失败；不会嵌入、刷新元数据或清理旧索引。合法空目录也必须完整走完“事务成功 → 空完成帧 → EOF”。
- Agent 的目标索引会话锁仍在调用 Mall 前获取，覆盖整个扫描/嵌入/发布流程。Mall 的源事务仅覆盖目录读取和发送，不跨越 Embedding；之后 Agent 用原有短事务原子发布。这是两个独立数据库边界，不是跨服务分布式事务。
- 流式鉴权复用与一元接口相同的命名密钥、调用方/受众/用途策略，生产 Mall 显式注册流式服务端拦截器；Agent 的专用流式拦截器仅允许此方法。旧 `ListProductIndex` 保留原权限，用户/支付链路不改成服务索引身份。Token 在建流时校验，不逐帧重新验签，也没有新增流中途撤销协议。

资源边界由双方共用的 [indexcontract](../services/rpc/mall/indexcontract/contract.go) 定义，目前是固定安全上限，不新增环境变量：

| 资源 | 当前边界 |
| --- | --- |
| 每页 SKU | 默认 100，最多 200 |
| 全目录 SKU | 最多 50,000；超过则整轮失败，不截断成完整目录 |
| 每帧 protobuf 载荷 | 最多 2 MiB；Agent 同时设置 gRPC 接收上限 |
| 全流 protobuf 载荷 | 最多 32 MiB，包含完成帧；不是 Go 堆内存或 HTTP/2 字节的硬配额 |
| RPC 总时限 | 最多 30 秒，且不能延长父轮次的较早 deadline |
| Mall 并发快照 | 每个生产模型/服务实例最多 1 个；忙时 `ResourceExhausted`，不是跨副本全局配额 |

Mall 要求原始流 context 已带 30 秒以内的 deadline；方法策略 `MaxStreamDuration` 在鉴权后、生成 handler 的首次 `RecvMsg` 前拒绝缺失/过长 deadline，logic 和模型再次防御，防止只建流不发请求的客户端长期挂起。只给业务函数派生 timeout 不能中断原始流上的阻塞 `Send` / `Recv`，因此这里依赖 gRPC 传输 deadline 传播及数据库驱动响应 context，不另起无法回收的发送协程。[gRPC deadline 文档](https://grpc.io/docs/guides/deadlines/)说明了服务端取消与应用主动停止后续工作的责任。取消或发送失败回滚源事务，不发送成功终帧；具体故障清理时延仍需真实环境验收。

升级时先部署支持新 RPC 的 Mall，再更新 Agent。旧 Mall 的 `Unimplemented`、权限失败、超时或容量不足均保留旧索引，不回退到旧实时分页。M3.2b1 的停旧同步器、存量索引绑定迁移及连接池限制仍必须遵守。本步不提供断点续传、增量 CDC、大目录外排、自动拆分或模型热迁移；目录与待发布向量仍驻留 Agent 内存，单个数据库字段在序列化限额检查前也已读入内存，不能把载荷限额当成经过压测的内存保证。

本地驱动替身验证了事务选项、连接绑定、游标参数、提交/回滚与取消边界；内存 gRPC 覆盖完成/断流/迟到错误/慢接收者。另提供 [真实 PostgreSQL 并发更新测试](../services/rpc/mall/model/product_index/snapshot_integration_test.go)，仅在显式提供可丢弃的 `BUDGETMATCH_TEST_POSTGRES_DSN` 时执行，创建并清理随机隔离 schema；本次跳过，不能写成真实数据库 MVCC 已验收。

### 2.13 候选证据与严格实时校验（M3.2c）

生产依赖组装按 Mall 配置选择返回策略：配置 `MallRpc` 就强制校验，无 Mall 才使用带明确标识的演示模式。规则推荐、ReAct 成功和模型失败后的规则兜底，都先完成结构化结果校验，再经过同一个 Finalizer，最后才保存和返回。Finalizer 失败不再降级执行其他 Agent；该轮次不保存，依赖恢复后可以重试。

- `ProductCandidate.Evidence` 保存类型化来源（关键词/向量/演示）、所属 SPU、向量相关性及其是否存在、快照/检索时间和核验状态。字段来自可信 Provider，不从模型回答反序列化，也不凭展示字符串 `Source` 授信；证据及模型选择范围均为请求内数据，不发送给模型、不进入公开 JSON 或会话结果。
- 新索引 metadata 的 `snapshot_at_unix_ms` 是 Agent 观察到的扫描开始时间，不是数据库精确快照时刻或行更新时间；同一扫描使用同一值。旧索引缺失此字段、关键词列表的缓存年龄以及固定演示数据的快照时间均为未知（0），不伪造新鲜度。时间、价格和库存变化只刷新 metadata，不改变嵌入文本/内容哈希。
- 正常 Mall 模式将已选 SKU 优先、再按既有选择器顺序补充备选，最多检查 32 个。模型最后一次 `select_bundle` 的候选 ID 范围以及更紧预算/件数会保留；当时为空的 ID 参数表示“选择时已缓存的全部候选”，不自动纳入后续搜索。规则及未显式选择的内部兜底使用已有检索候选。
- 新 `mall.ProductService/CheckProductCandidates` 是普通用户 JWT 的只读 RPC。它以一次参数化 SQL 联接 SPU/SKU，直接读取价格、库存、销量和名称，要求双方均上架且未软删除；不使用有缓存的 `GetProduct`，不读取所有者、订单、内部评价或商品长正文。每个请求 ID 必须有一个明确回答：`ACTIVE`（仍可能库存为零）或 `UNAVAILABLE`（已确认不存在/下架/删除）。数据库失败返回依赖错误，不能伪装成商品不存在。
- Agent 拒绝缺项、重复/额外 ID、未知状态、矛盾字段、SPU 身份变化、明显异常时间及超限响应。确认不可用、无库存或非法价格的商品剔除；其余用核验后的价格/库存/销量/名称重新选择，并再次核对预算、件数与总价。Mall 没有权威品类字段，不能给旧向量品类背书，最终 Mall 条目的 `Category` 保持未知。
- RPC 不可用、旧 Mall 不支持、私有核验期限耗尽或响应异常时返回 `Unavailable`，不输出旧快照或混入 Mock；用户取消/父 deadline 和鉴权错误保留终止语义。全部商品被**确认不可用**时可以返回空组合，不等同于全部核验请求失败。根本没有候选时不发空批请求，也不宣称已完成实时核验。

| 边界 | 当前实现 |
| --- | --- |
| 校验批次 | 每轮最终结果最多 1 次 RPC、32 个唯一 SKU；ID 最多 64 字节 |
| 核验时限 | Agent 与 Mall 各设置最多 2 秒子 context，父 deadline 更早则优先；不是整个推荐请求的时限 |
| 响应大小 | protobuf 最多 64 KiB；Agent 同时限制 gRPC 接收消息，Mall 返回前检查大小 |
| 时间容差 | Mall 返回查询开始时间；Agent 接受本次调用窗口前后最多 30 秒主机时钟偏差，超出则拒绝，需要运维时间同步 |
| 重选范围 | 仅当前 shortlist；不再次搜索、不反复校验、不承诺最优或全局无解 |

成功摘要记录 UTC 核验时间，并说明“仅代表核验时点，下单前重新确认价格和库存”，`ToolsUsed` 增加脱敏后的 `candidate.verify`。历史查询和相同 `turn_id` 重试原样重放首次金额、摘要与核验时间，不重新查询；旧历史也不会被追溯标记为已核验。核验不预占库存，校验到显示/下单之间仍可能变化。无 Mall 时摘要明确为“演示数据，非实时商城库存”，演示候选不能通过 Mall 严格策略。

升级先更新 Mall，再更新 Agent。旧 `RAG.VerifySku` 仅保留配置兼容字段，其值已忽略，不能用 `false` 关闭最终校验；新的关键词和向量路径都必经此步骤。新 RPC 不需要数据库迁移、索引服务凭据或新的 HTTP 路由；历史 metadata 缺失时间不阻止在线核验。

范围限制：这个策略保护统一推荐响应与会话持久化，**不追溯重写模型在 Finalizer 前通过文件工具生成的草稿**；草稿不是已核验报价。旧快照在检索阶段已经过滤掉的商品不会因本次价格下降/补货被重新召回，完整召回和质量排序留待 M3.3/M4。现有固定快照评测继续不装配在线 Finalizer，以保持基线协议；专用服务/脚本模型/RPC 测试验证新策略，不将固定评测通过当作真实 Mall 验收。载荷限制也不等于单个异常数据库字段的读取内存上限。

代码入口：[候选证据](../services/rpc/agent/internal/agent/candidate_evidence.go)、[统一 Finalizer](../services/rpc/agent/internal/agent/recommend/finalizer.go)、[商城校验客户端](../services/rpc/agent/internal/tools/candidate_verifier.go)、[商城只读查询](../services/rpc/mall/model/product_index/candidates.go)。[真实 PostgreSQL 新鲜度用例](../services/rpc/mall/model/product_index/candidates_integration_test.go) 仅在显式可丢弃 DSN 下执行，本次未运行。

| --- | --- | --- |
| Agent 编排 | Eino ReAct 调用商品搜索、组合选择、文件和 MCP 工具；请求级 Session 收集类型化结果 | 不能只依赖 Prompt 限制模型；工具参数和最终结果需要统一业务校验 |
| 预算与件数 | Planner 合并当前输入、历史状态和默认值；选择器执行传入的预算与数量限制 | `select_bundle` 只对非正参数回退；模型传入更大正值可能放宽用户约束 |
| 商品组合 | 价格、销量、库存等启发式评分后贪心选择 | 未实现需求品类覆盖和搭配约束；不能声称全局最优 |
| RAG | 向量优先、关键词回退；内容哈希与模型指纹决定增量重嵌入 | 不是混合召回；检索相关性未进入统一组合评分；缺少固定效果评测集 |
| 数据新鲜度 | 支持通过 Mall 查询 SKU 刷新快照 | 查询失败时仍保留快照；“可展示”与“已校验”没有显式区分 |
| 后台索引 | 启动及定时同步商品文档 | 后台 `context.Background()` 无用户 Token，而 Mall 商品读取要求认证；据调用链推断存在鉴权阻碍，需真实联调验证 |
| 会话记忆 | PostgreSQL 事实源、Redis 版本化快照、结构化约束持久化 | 应补真实多实例、缓存失效失败和持锁连接占用测试 |
| 请求幂等 | 用户＋会话＋轮次标识定位已完成结果；内容不同返回冲突 | 不是外部模型调用的 exactly-once；模型完成后、入库前故障可能导致重算 |
| 上下文 | 初始消息按近似 Token 预算保留完整历史轮次；限制 ReAct 最大步数 | 不是整个执行过程的严格 Token 上限；工具结果和中间消息也会消耗上下文 |
| 流式接口 | HTTP SSE 包装受理、RPC 开始、最终结果等事件 | 底层仍为 unary RPC；未贯通模型内容和工具事件流 |
| 工具安全与观测 | 文件路径/后缀限制；Eino 回调记录耗时、Token 用量与工具内容 | 文件工作区尚未按用户隔离；工具内容截断不等于脱敏；MCP 每请求创建子进程 |

## 4. 目标架构与不变量

```text
认证用户请求
  → 会话级锁 / 已完成轮次重放
  → 服务端解析有效约束
  → ReAct 工具编排（异常时进入规则路径）
  → 候选检索 / SKU 去重 / 数据校验
  → 受约束组合选择
  → 统一结果校验 / Mall 严格核验并有界重选（无 Mall 时明确演示）
  → 事务保存会话状态和完整结果
  → 返回最终结果（同步响应或流式 final）
```

主验收模式为 PostgreSQL＋Redis。Redis-only 和 InMemory 保留为短期/演示模式：完成表示当前存储的轮次保存成功，不承诺服务重启、TTL 到期或存储丢失后仍可恢复。

必须保持以下不变量：

1. 用户身份只来自认证上下文，不接受模型参数或客户端字段替代身份。
2. 有效预算和件数由服务端确定，模型只可收紧，不能放宽。
3. LLM 与规则路径共享结果校验；降级不是绕过约束的入口。
4. 商品 ID、价格和库存来自商品数据源，模型文本不是业务事实来源。
5. 只有轮次保存成功的完整结果才能标记为完成；PostgreSQL 模式必须事务提交成功，数据库失败不能伪装成成功。
6. Redis 故障不覆盖 PostgreSQL 事实；已完成轮次重放不重新检索或调用模型。
7. 请求取消后不启动新的模型、工具或兜底调用；已经完成的外部副作用不能假定已撤销。
8. 推荐时的库存校验不等于库存预占，下单仍由 Mall 重新确认价格和库存。

范围之外：自动下单/支付、全站权限重构、生产 SLA 承诺、无评测依据的模型升级，以及外部工具副作用的 exactly-once 保证。RAG 所需的最小 Mall 服务认证改动属于本方案，但应单独评审和提交。

## 6. M1：业务约束与基础安全

### 6.1 统一有效约束

在 Agent 领域层增加约束解析与校验组件，避免规则 Agent、LLM 工具、最终响应各自维护不同规则。

- 优先级：当前轮显式结构化字段 → 当前轮明确文本 → 已保存结构化状态 → 现有默认值。
- 保留现有 `0` 表示未显式指定的语义；增加“取消预算”等能力时使用独立字段，不挪用 `0`。
- 保留当前外部边界：预算上限 `100000000000` 分、件数上限 `10`；文本解析、历史恢复也必须经过边界校验。
- 金额统一使用人民币整数分。无法明确币种或存在矛盾的文本不能按隐含汇率换算；返回可解释的校验错误，后续接入澄清状态。
- 显式非法输入拒绝处理；仅缺省值使用默认值，不将非法值静默修正为默认预算。

工具参数策略：

1. 预算和件数为 `0` 时继承有效约束；负数视为非法参数。
2. 正数超过有效上限时收紧到该上限，并记录脱敏的约束调整原因。
3. 搜索和选择工具使用同一约束，防止只在最后一步校验导致无效候选大量进入上下文。
4. 限制工具请求中的候选 ID 数量、搜索文本和关键词数量，防止放大 RPC 查询与内存开销。

### 6.2 候选和结果校验

- 同一 SKU 只保留一个候选；当前接口没有购买数量字段，因此相同 ID 不得作为多个条目重复计数。
- 第一版拒绝空 ID、非正价格、负库存等异常数据；如以后支持免费商品，另行定义零价策略。
- 商品只能来自本轮检索得到的候选集合；未知 ID 不得进入最终结果。
- 总价由服务端重新计算，执行整数溢出检查，并验证预算、件数和条目价格一致性。
- 商品校验或重选改变组合时，丢弃旧的模型价格说明，改用基于最终事实的确定性摘要。
- 不仅检查结构化条目，也测试模型 Summary 与实际方案矛盾的情况；第一版无法可靠核验的价格/库存承诺不交由模型自由生成。
- 校验失败最多进行一次有界规则重选，仍不合法则返回业务错误或明确的候选不足结果；不无限自我修复。

最终校验接入业务编排层；Agent 内部保留足够的候选证据供校验，不能把未经验证的 Result 再当作证据。M3 再接入商城实时校验策略，M1 不声称已经解决库存时效问题。

### 6.3 工具隔离与敏感信息

- 文件工具默认不启用；启用时根据可信用户 ID 映射独立工作区，不把用户 ID 直接拼接成可穿越路径。
- 继续限制相对路径、符号链接逃逸和文件类型；补写入大小、目录权限与跨用户访问测试。并发路径替换需采用目录约束的文件操作，不能只依赖“先检查再打开”。
- MCP 默认关闭；启用后按配置白名单暴露工具，不将整个外部工具列表无条件交给模型。
- 工具输出、商品描述和文件内容均作为不可信数据，不能改变用户身份、预算或权限策略。
- 日志和 `ToolsUsed.Detail` 默认仅保留工具名、状态、错误分类、数量与耗时；不返回文件正文、Token、密钥或原始内部错误。
- 第一阶段不开放下单、支付等有外部业务副作用的工具；文件写入需要用户明确保存意图，不能假定重试无副作用。

### 6.4 验收

- 模型放大预算/件数、重复 ID、伪造 ID、负价、整数边界、历史非法状态均有回归用例。
- LLM 与规则两条路径执行同一组约束测试；随机输入下不输出违反硬约束的完成结果。
- 跨用户文件访问被拒绝，日志及客户端工具记录不泄露测试植入的敏感标记。
- 身份错误、参数错误和已取消请求不通过规则降级掩盖；原有会话与幂等用例不退化。

### 7.1 数据与执行器

M2.1 已新增 `services/rpc/agent/testdata/eval/` 存放合成快照、JSONL 用例和首版报告，`services/rpc/agent/internal/eval/` 实现执行与指标，`services/rpc/agent/cmd/eval/` 提供离线 CLI。它复用现有 Planner、Service、BundleSelector 与 InMemory 会话，仅替换商品 I/O，不修改线上推荐策略。

M2.2 修复 Planner 的两条预算变更表达，并增加同数据版本对比与独立脚本模型容错套件。原始 64 条用例、商品快照和 `baseline.v1` 均未改写；规则结果另存 `baseline.v2`。本次已使用 holdout 中的已知失败修复代码，因此现有 holdout 只作为固定回归集，不再声称是未见盲测；未来泛化评价需在独立复核后另建未见测试集。

首版 `synthetic-products-v1` 包含 21 个商品、64 条用例，固定分为 dev 31 条 / holdout 33 条，标注同族改写和完全相同的执行输入不跨集合。归档前修正了初稿的重复输入跨集合，以及“静音鼠标/机械键盘”未限定对应属性 SKU 的标注问题，未修改被测推荐策略或通过线。快照声明 `synthetic` / `pending_human_review`，通过程序引用/限额/组合可行性检查，**尚未经独立人工复核**；按用户决定收尾 M2 不代表下面原定“60 条人工核对”的目标已验收。

第一版目标为不少于 60 条人工核对用例，至少覆盖单品、多品类、预算不足、缺货/下架、噪声商品、多轮约束覆盖、冲突输入、提示注入和依赖故障。每条记录包括：

- 用例 ID、场景、商品快照版本、查询与历史轮次。
- 显式约束、可接受 SKU 集合、必需需求及预期结果状态。
- 对可满足/不可满足/需要澄清的人工标注；主观偏好使用允许集合，不限定唯一答案。
- 调参集与保留测试集固定划分；模型、Prompt、Embedding、策略和代码版本纳入运行元数据。

当前离线入口（从仓库根目录执行，不读取 `.env`、不启动数据库/MCP、不调用付费 API）：

```bash
# stdout 输出 JSON；当前全量规则评测门禁通过，退出码为 0（不代表全部推荐任务成功）
go run ./services/rpc/agent/cmd/eval -revision '<实际提交号或提交号+worktree>'

# 同一次执行生成机器可读明细和 Markdown 汇总；目录必须不存在，父目录必须已存在
go run ./services/rpc/agent/cmd/eval -split all -top-k 10 \
  -revision '<实际提交号或提交号+worktree>' -out /tmp/agent-eval-run-001

# 独立查看保留集或直接输出 Markdown
go run ./services/rpc/agent/cmd/eval -split holdout -format markdown

# 与原始报告逐例对比：必须使用相同数据哈希、划分、TopK 和测量口径
go run ./services/rpc/agent/cmd/eval \
  -compare services/rpc/agent/testdata/eval/baseline.v1/report.json \
  -revision '<实际提交号或提交号+worktree>' -format markdown

# 独立的脚本模型套件，不混入 64 条规则用例的质量指标
go run ./services/rpc/agent/cmd/eval -suite scripted \
  -revision '<实际提交号或提交号+worktree>' -format markdown
```

`-snapshot` / `-cases` 可显式指定文件；输入最大 4 MiB、最多 256 商品 / 1000 用例 / 10 个历史轮次，单行 JSONL 最大 64 KiB，拒绝未知字段、错误 SKU 引用、同族跨集合和自相矛盾的可行性标注。报告包含输入文件 SHA-256、调用者提供的代码标记、策略版本、Go/OS/架构/逻辑 CPU、并发、缓存策略、TopK 和划分；未提供代码标记时写 `unknown`，不会伪造提交来源。

退出码：`0` 表示安全/预期终态/持久化/重放门禁通过；`1` 表示评测已完成但门禁未通过（仍输出完整报告）；`2` 表示参数、数据或执行器错误。`go run` 会额外打印子程序退出状态，自动化如需精确区分 `1/2` 应先构建二进制。推荐质量不设事后放宽的通过线，所有可满足失败样本继续保留；即便门禁通过也不代表任务成功率为 100%。

输出目录使用独占创建，不覆盖历史报告；若写入中断，目录可能保留部分文件，下次应选择新目录。首版归档见 [Markdown 报告](../services/rpc/agent/testdata/eval/baseline.v1/report.md) / [JSON 明细](../services/rpc/agent/testdata/eval/baseline.v1/report.json)。不因结果不理想移动 holdout、删除反例或改写标注；后续数据修订需说明理由并变更版本，原始基线保留。

M2.2 规则归档见 [对比报告](../services/rpc/agent/testdata/eval/baseline.v2/report.md) / [JSON](../services/rpc/agent/testdata/eval/baseline.v2/report.json)，脚本套件见 [容错报告](../services/rpc/agent/testdata/eval/scripted.v1/report.md) / [JSON](../services/rpc/agent/testdata/eval/scripted.v1/report.json)。`-compare` 只支持规则报告，拒绝不兼容的元数据、重复/缺失用例和汇总不符；对比列出终态/任务改善与退化，不放宽质量阈值，也不把未控制负载下的延迟差异解释为性能收益。报告来源标记由调用者提供，并非提交签名或防篡改认证。

`-suite scripted` 固定使用代码内的 16 个脚本和 2 个合成商品，拒绝 `-snapshot/-cases/-split/-top-k/-compare`，支持同样的 `-format/-revision/-out`。分别记录服务级规则兜底和模型未选择时的内部选择兜底、期望/实际调用数、工具反馈、硬约束、公开正文脱敏、持久化和重放检查；任一检查失败退出 1。脚本/快照 SHA-256 与实际系统 Prompt 指纹纳入报告。文件/MCP 默认关闭，不使用真实模型。

模型错误恢复用脚本化 Fake Model 验证；确定性回归默认不访问外网。合成向量只能证明检索代码行为，不能证明真实语义质量。外部模型/Embedding 评测单独启用，执行前确认凭据、数据范围、次数与费用上限，不自动读取 `.env` 批量付费调用。

### 7.2 对照方案与指标

使用相同快照、用例划分和硬约束比较三条基线：关键词＋规则、向量＋规则、向量＋ReAct。每条分别统计降级比例，不能把规则兜底的效果算成模型成功。

规则质量套件仍只执行关键词＋规则：离线适配器过滤下架/缺货/超预算商品，按商品文本命中关键词数降序、SKU ID 升序取 TopK，无匹配时返回空；它不等同于真实 Mall 搜索。另两条基线明确记录 `not_run`，不填语义/模型成功率。该套件的故障恢复仍使用确定性 Agent 替身注入 primary Unavailable，以及商品源 Unavailable/PermissionDenied，不把它误记为模型调用。

M2.2 的独立套件接入真实 Eino ReAct、业务工具和 Service，用 Fake Model 脚本生成工具调用/异常。覆盖正常编排、缺少选择、畸形 JSON/负限额/未知 SKU 的反馈后修正、抬高限额、模型不可用（含选择之后失败）、商品源瞬时故障、未知工具、步数耗尽、模型/工具权限拒绝、取消/超时及模型前拒绝。当前 16/16 通过、脚本模型调用 33 次、完成轮次重放 11/11；这是代码容错证据，不是模型能自主纠错、具备语义能力或抵抗注入的证据。超时用 `DeadlineExceeded` 注入，未测真实墙钟截止；MaxStep 是当前锁定 Eino 的图节点步数，不等于模型调用次数。

| 指标 | 口径 |
| --- | --- |
| 硬约束违规率 | 完成结果中超预算、超件数、重复/未知 ID、错误金额等违规比例；另报全部请求中的违规数 |
| 可满足任务成功率 | 标注为可满足的用例中，返回合法且覆盖所需需求的比例，避免空结果刷高安全指标 |
| 需求覆盖率 | 满足的必需需求数 / 标注必需需求数；没有必需需求的用例不混入该分母 |
| Recall@K | 过滤后 TopK 中命中的标注相关 SKU 数 / 标注相关 SKU 总数；无相关商品用例单独报告 |
| 事实一致性 | ID、价格、总价由代码比对；解释文本人工抽检，可选辅助模型评审 |
| 性能与成本 | 端到端 P50/P95、阶段耗时、模型/工具调用次数、提供商返回的 Token 用量、索引新增嵌入量 |
| 容错与幂等 | 降级率、错误类别、已完成轮次重放时新增模型调用数及新增持久化轮次数 |

当前指标实现约定：

- 预算/件数使用每条用例的独立预期值，商品事实使用固定快照，不信任被测结果自带的候选或约束；相同 SKU 不可重复计召回/需求。
- 可满足成功必须非空、合法、覆盖全部必需需求且只含允许 SKU。空结果可能安全，但不能提高该成功率；非法完成结果的需求覆盖记零。
- Recall@K 使用 micro 汇总（相关 SKU 命中总数 / 标注相关 SKU 总数）；无相关 SKU 用例单列，不计分母。需求覆盖包含标注不可满足需求，理论上不必达到 100%。
- 无有效样本的比例为 `null`；不把“未测量”记为零错误或 100% 成功。Token/费用没有提供商数据，明确未测量；规则套件模型调用为 0，脚本套件的 Fake Model 调用单列，不能充当外部模型成功率。
- 每例使用全新内存会话，历史先经业务服务正常执行；仅计当前测量轮次的推荐延迟，历史准备/重放另计。P50/P95 使用 nearest-rank，单线程同进程、无显式预热；不是生产容量/延迟结论。
- 成功轮次立即以原用户/会话/turn_id 重放，比较完整公开结果、查询/故障替身调用增量及完成轮次数；拒绝/错误不能新增完成轮次。当前不证明 PostgreSQL 多实例或真实模型幂等性。

回答忠实度和检索质量的辅助评测可参考 [Ragas 指标定义](https://docs.ragas.io/en/v0.4.1/concepts/metrics/available_metrics/)。本项目的预算、金额与库存约束由程序和固定快照判定，不由模型评审替代。

### 7.4 M2.3：人工复核材料与流程

M2.3a 只完成可自动化的准备工作：提供 [64 条用例复核工作单](../services/rpc/agent/testdata/eval/review.v1/review.md)、[全 pending 的 JSON 模板](../services/rpc/agent/testdata/eval/review.v1/review.json) 和 `cmd/eval-review`。它们不是第二份开发计划；技术口径、目标和进度仍以本文为唯一入口。工作单包含完整 21 个商品、原始查询、历史顺序和待复核标注，不读取策略报告，不展示当前推荐结果，也不运行推荐器或外部客户端。

```bash
# 生成新的独立工作目录；不能覆盖已有目录或归档模板
go run ./services/rpc/agent/cmd/eval-review \
  -revision '<实际提交号或提交号+worktree>' -out /tmp/agent-review-001

# 人工填写 /tmp/agent-review-001/review.json 后进行记录校验
go run ./services/rpc/agent/cmd/eval-review \
  -check /tmp/agent-review-001/review.json -format markdown
```

生成模式退出 0 只表示成功生成待填写材料。校验模式：0 表示声明/记录齐全，1 表示尚有 pending、changes_requested 或缺少人工/独立性/快照核对声明，2 表示格式、数据绑定或字段组合非法。自动化需区分精确退出码时先构建二进制，`go run` 可能将非零退出折叠为 1。`-snapshot/-cases` 可指定版本，始终检查全部用例，不支持只复核 dev 或挑选通过样本；`-check` 不允许同时传 `-out/-revision`。

填写及验收规则：

1. 由未生成原始标注的人工复核者先依据查询/历史和全量商品独立判断，再对照待复核标注；现有 holdout 已被用于修复代码，不能重新宣称是盲测。复核者填写可追溯的非敏感 ID/别名，并如实声明 `human`、`independent` 与 `snapshot_checked`，不要填写密码、Token 或不必要的个人信息。
2. 每条核对六项：约束优先级及数值、必需需求、三类 SKU 集合的语义、可行性、预期终态/故障、用例族与划分。核对“静音/机械”等属性及没有列入标注的候选；不可满足、无相关 SKU 和拒绝样本也要复核，不能只审 40 条可满足任务。
3. `accepted` 必须完成六项 checks、填写复核者和含时区的 RFC3339 `reviewed_at`；有疑问使用 `changes_requested`，在 `notes` 写原因和修订建议，未处理保持 `pending`。只编辑 JSON，工作单 Markdown 不作为机器记录；归档的 `review.v1` 永远保留空白模板，实际复核记录另存。
4. 校验器检查整个快照/JSONL 文件哈希、逐例规范 JSON 指纹、ID 全覆盖及唯一性、状态/时间/检查项、备注长度与未知字段。任何输入或标注变化都会使旧记录失配；模板不能自动继承到修订后的数据集。
5. `records_complete=true` 仍只是填写者的自我声明通过结构检查。工具始终报告 `human_identity_verified=false`、`acceptance_status=not_performed`，不认证签名、人工身份或判断正确性，不修改原始 `annotation_status`，不作为费用授权或 M2 自动验收按钮。
6. 有标注异议时先由负责人裁决；若需修订，另建数据版本、说明原因并重跑旧策略基线，再调整目标草案，保留原始数据/报告。不得为了达到阈值删除反例或回写旧版。M2.3b 需负责人核验实际复核材料、确认下节目标并记录数据哈希/批准人/批准日期后才可关闭。

当前归档模板的实际状态：64 条 pending、0 条 accepted，无复核者声明；独立人工复核尚未完成。2026-09-17 用户决定收尾 M2、先推进 M3，故 M2.3b 后置且不再作为 M3 本地实现的阻塞条件；模板、原始标注和历史报告保持不变。生成材料、自动检查或用户调整开发顺序均不能代替独立人工复核。

### 8.3 检索实验

先保留现有向量优先/关键词回退作为基线，再提供可配置的实验策略：

1. 关键词与向量两路有界召回，按 SKU 去重并保留各自排序。

- 内部意图扩展为预算、件数、必需需求、可选需求、排除条件和偏好；模型抽取只是提议，经过 Schema 和服务端规则校验后才进入有效状态。
- 区分当前轮覆盖、追加和移除条件，避免偏好永久累加无法撤销；同一轮的互斥需求进入澄清状态。
- 不确定的分类标为 unknown，不算作满足硬品类约束；不伪造主板接口等兼容性信息。

### 9.2 选择策略

保留现有贪心选择器作为基线；新增有界 Beam Search 作为实验实现，不承诺全局最优。

- 硬约束：预算、最多件数、SKU 唯一、可用状态，以及用户明确要求的必需需求和排除条件。
- 软目标：需求相关性、偏好匹配、功能互补和性价比；预算利用率只作参考，不鼓励为了花满预算添加无关商品。
- 设置候选数量、Beam 宽度、扩展次数和计算时间上限，固定排序和同分决策规则，保证结果可复现。
- 先过滤非法候选，再搜索可行组合；硬约束不允许被评分补偿。
- 达到搜索上限时只能返回已验证的可行解或“在当前候选/搜索范围内未找到”，不能将有界搜索失败表述为全局无解。
- 从选中 SKU、满足的需求及已知不足生成结构化解释，再由模型润色；涉及价格和库存的字段以服务端事实为准。

新增结果状态建议为 `complete`、`partial`、`needs_clarification`、`no_feasible_bundle`，配合 `missing_requirements` 与原因分类。`partial` 明确不是完成全部需求，不能计入可满足任务成功率。`no_feasible_bundle` 必须说明当前候选/搜索边界；只有有证明的测试样本才标注全局不可满足。

验收：至少包含“单个高分商品阻挡完整套装”的贪心反例、多品类必选、排除条件、预算不足、未知类别、多轮撤销偏好和搜索超时用例；硬约束零违规，并报告需求覆盖率相对基线的变化及计算开销。没有改善则继续使用基线。

## 10. M5：端到端流式、运行预算与可观测性

### 10.1 流式链路及鉴权

新增 `RecommendStream` 服务端流式 RPC，保留 `Recommend` unary RPC。二者共享约束、幂等、校验和持久化流程，不维护两套业务逻辑。

```text
浏览器带认证的 POST + fetch
  → App Gateway SSE
  → 带认证 metadata 的 gRPC server stream
  → Agent 执行器 / Eino Stream 与工具回调
  → 校验 + 持久化
  → final + done
```

Eino ReAct 提供流式执行能力，具体接入以 [go.mod](../go.mod) 锁定版本及本地源码为准，不直接套用最新版文档示例。框架流程参考 [Eino ReAct 官方说明](https://www.cloudwego.io/docs/eino/core_modules/flow_integration_components/react_agent_manual/)。

- 当前项目注册的是 unary 认证拦截器。新 RPC 上线前必须增加 stream 服务端鉴权、可信身份注入、客户端 Token 透传及对应错误映射。
- HTTP 网关仍执行已有认证；直接访问 streaming RPC 也必须通过认证。测试伪造 metadata、无 Token、过期 Token 与跨用户同名会话。
- 核对网关、RPC 客户端、RPC 服务端、模型超时与代理空闲超时，显式配置并传播剩余 deadline；不能只增大模型超时。
- HTTP 开始流之前的错误使用正常状态码；流开始后通过脱敏 `error` 事件传递，不能尝试重新写 HTTP 状态。

### 10.2 事件协议与完成语义

保留已有 `request.accepted`、`rpc.started`、`recommendation.final`、`done`、`error` 名称；新增事件字段向后兼容，客户端忽略不认识的事件。

| 事件 | 内容与约束 |
| --- | --- |
| `request.accepted` | 返回稳定的会话、轮次和本次执行标识，不代表已经完成 |
| `tool.started` / `tool.completed` | 工具名、关联 ID、状态和耗时；不发原始参数、文件正文或内部推理 |
| `answer.delta` | 面向用户的解释增量，带序号并标记为临时文本；不是可下单的最终方案 |
| `recommendation.final` | 只在校验和事务保存成功后发送，包含完整业务结果；前端以此替换临时展示 |
| `error` | 公共错误码、可展示文案和是否允许重试；不泄露内部错误 |
| `done` | 正常连接下的终止标记，区分成功/失败；断连时不保证送达 |

- 只推送用户可见的最终回答流和可公开的工具状态，不推送隐藏推理、工具参数片段或原始内部消息。
- 商品卡片和下单入口仅由 `recommendation.final` 驱动。临时文本若被最终校验推翻，必须替换或清除；不能同时展示互相矛盾的方案。
- 一个执行流正常成功时仅有一次 final 和一次 done；网络可能中断或重放，因此前端按轮次、执行标识和事件序号处理，不宣称网络事件恰好一次。
- 客户端首轮也预生成 `conversation_id` 与 `turn_id`，重试保持不变；旧客户端仍可省略，但未拿到服务端 ID 的失败首轮不承诺跨请求幂等。
- 已完成轮次只重放 final/done，不重演工具副作用；第一版不支持按 `Last-Event-ID` 恢复未完成的 Token 流。
- 客户端断开后取消未完成推理；若事务已提交但 final 未送达，使用相同标识重试恢复已保存结果。

### 10.3 有界执行与观测

- 限制全请求时长、锁等待时间、工具并发与输出大小、模型调用次数和 ReAct 步数；保留少量时间给校验与保存。
- 每次模型调用前估算剩余上下文，覆盖系统消息、工具 Schema、中间消息和工具输出；保持 tool call/result 配对，不随意裁掉半组消息。
- 近似估算不是供应商精确 Token 计费；实际 Usage 单独记录，缺失时标记 unknown，不写成 0。
- 取消和 deadline 是终止信号，不进入普通工具错误的自我重试；上下文不够、认证失败与不可恢复错误有独立分类。
- 事件传递使用有界队列，慢客户端通过背压或超时取消处理；心跳不代表模型已产出，首个回答增量耗时单独计量。
- 复用已有 Eino 耗时/Token 日志，增加请求级汇总、检索来源、降级原因、重放命中、锁等待、首个回答增量及总耗时。
- 用户/会话/轮次标识只进入受控日志或 trace，不作为 Prometheus 高基数标签；工具日志按 M1 脱敏规则输出。
- MCP 子进程池化不是必做项；先补启动/调用并发上限、超时和清理测试，再依据耗时证据决定是否复用，防止跨用户状态串用。

验收：Fake Stream 在 final 前产生可见回答增量，工具状态正确关联；直接 RPC 无认证被拒绝；取消、慢消费者和中途错误不产生虚假的完成轮次或泄漏任务；同步与流式相同请求得到同一持久化结果。真实模型首个增量时延另行实测。

## 11. M6：并发、故障与交付验证

使用独立、可丢弃的 PostgreSQL/pgvector 与 Redis 测试环境，至少覆盖以下矩阵：

| 场景 | 必须验证的行为 |
| --- | --- |
| 两个 Agent 实例并发提交同一轮次 | 正常运行且保存成功时只新增一轮，其余请求返回同一结果 |
| 同一会话不同轮次 / 不同会话并发 | 前者串行且后者不被全局锁阻塞；不承诺不同请求的到达顺序就是执行顺序 |
| 不同用户复用相同会话/轮次 ID | 历史、状态、结果及文件均隔离 |
| 保存后 Redis 失效失败 | 旧版本快照不能命中，回源正确；数据库写入失败则不得误报成功 |
| 模型完成但尚未入库时进程终止 | 没有完成记录；重试可能再次推理，明确记录该幂等边界 |
| 事务提交后、响应发送前断连 | 重试返回持久化结果，不新增轮次 |
| 删除会话与推荐并发 | 删除与推荐使用相同锁；行为按获得锁的顺序确定，不凭空承诺禁止后续重建 |
| 长模型调用与锁等待取消 | 锁可释放、专用连接可归还；统计连接池等待及占用时间 |
| Redis-only 锁租约到期 | 不允许旧持有者继续提交；选择有界执行、续租及提交令牌校验，不能只依赖令牌解锁 |
| 模型/向量/Mall 失败 | 合法降级或明确错误；无未校验商品混入，无无限重试 |
| SSE 取消、慢客户端及代理断连 | 释放流、goroutine、模型请求和 MCP 进程，已提交结果仍可恢复 |
| 索引分页中断、部分更新或身份失效 | 不误清理索引；失败可观察，恢复后可重新同步 |

当前 PostgreSQL advisory lock 在推理期间占用专用连接，因此不能无依据宣称高并发。先测并限制并发与等待时间；若连接池成为瓶颈，再单独设计带租约/版本比较的执行协调，不能直接去掉锁破坏顺序与幂等。

Redis-only 是短期存储模式，租约与持久性能力不同于 PostgreSQL 模式。两种模式分开验证，不能把 PostgreSQL 的结果套到 Redis-only 上。

交付材料包括：固定数据与配置版本、测试输出、性能/成本报告、故障复现步骤、演示流程、已知限制和回滚记录。简历只引用已复现的数据，注明样本规模和本地/测试环境。

## 12. 契约、配置与回滚

### 12.1 契约变更

- M1 尽量不改变外部请求结构；领域约束、候选证据和测试先落地。
- M4 的结果状态、缺失需求、校验时间等字段采用新增方式；已有字段和含义保持兼容。新增意图字段保存到记忆时同步扩展幂等请求比较，避免不同需求错误复用同一轮次结果。
- M5 在 [Agent Proto](../services/rpc/agent/proto/agent.proto) 新增流式方法，HTTP 保留现有路径和认证方式；数据库不保存每个 Token 事件。
- 如内部事件必须暴露到 API，先修改 [Agent API 定义](../cmd/app/desc/agent/agent.api) 及相关模板，再生成；不手改 `pb/`、`client/`、`types.go`、`routes.go` 或生成 handler。
- [Makefile](../Makefile) 的 `make api-all` 会影响多个模块，实现时检查完整生成差异，保留用户已有修改，不混入无关重写。

### 12.2 配置原则

拟新增的配置类别包括：检索策略、SKU 校验策略、组合搜索上限、执行总预算、工具白名单/用户工作区、服务身份与事件队列限制。具体键名随相应阶段实现后写入配置结构和样例，本文不提供可被误用的未实现 YAML。

- 安全校验和用户隔离不设“关闭后恢复旧漏洞”的开关；检索/组合/流式策略可独立回退。
- 无 LLM/Embedding 配置时继续支持规则/关键词模式；配置了 Mall 就不能自动混入 Mock。
- 只有真实需要新环境变量时才更新 `.env.example` 和密钥说明，不把普通调优项全部变成密钥配置；不提交 `.env`。
- 运行预算不能超过外层 deadline。Redis-only 模式还需证明锁租约覆盖执行或具备续租/过期提交保护。
- 新字段可缺省读取，旧会话不做破坏性重建；有存量结构变更时先做测试环境迁移与恢复演练。

### 12.3 发布与回滚顺序

1. 先部署兼容的新服务端及安全修复，保留 unary 接口和现有策略。
2. 在固定用例与真实联调通过后，分别启用新检索、新选择器，再启用流式前端。
3. 新策略异常时回到经过 M1 校验的规则/旧检索路径，不能回退到无约束版本。
4. 回滚流式时保留旧阶段事件模式或同步调用；不删除已保存会话与轮次。
5. 涉及真实数据的索引重建、数据迁移、服务重启或新增付费调用，执行前单独确认环境与影响范围。本次文档交付不执行这些操作。
